Some views depend on who the person is: the age on each result's day, ranges of your own by sex and age (Labs and ranges, here), and what is built on height.

A profile's owners and editors change these, and everyone it's shared with sees them. They're encrypted like the records and go with the profile's export. A share link shows them only if its owner ticks About this person.

They're never used to judge a result or to replace the range printed on a report. This isn't medical advice.

Lab name matches

Another lab's name for a test you have, charted with it. You match names when you review an import.

When a lab names a test differently (Plt Count), Sanguity charts it with the test you already have (Platelet Count).

Each match is this profile's: it names a test as one source reported it (its name, unit and code) and the test it's charted with, or keeps it as a test of its own. Later imports, pulls and results typed in follow it.

Changing or adding one can move the results already saved too: they're charted with the test you pick, and each still keeps the name its lab gave it. Removing one leaves the results where they are; the next import with that name asks again. Every change can be undone.

Names, above, only changes how a name is shown. Owners and editors change matches; everyone the profile is shared with sees them. A match an admin made for every profile is on Install's Lab name matches.

Accounts

An account for each person who signs in. Being an admin lets someone manage accounts; it doesn't show them anyone's records.

A new account gets a one-time password, and its person chooses their own at first sign-in. Records are shared profile by profile, by each profile's owners, on its Sharing page.

To manage accounts, turn on two-factor sign-in (the authenticator app) or add a passkey for your own account, under Settings → Sign-in and security. Admins need one as soon as the server has more than one account.

Backups

A checked copy of the records, accounts, and phone and watch data in the backups folder. Copy them off this server too.

The encryption key isn't in the backups. Keep a copy of the key file somewhere else, like a password manager or a USB stick in a drawer: without it no backup can be read, and nobody can recover it.

A backup holds the database (accounts, profiles, records, settings), each profile's documents and uploads, the setup build, and the watch receiver's data: its database for each profile, as it last saved it, and every upload from a phone it archived. Not in it: your original exports, the encryption key, and the configuration (.env, sources.json). Making one is safe while people use the app and phones upload.

A backup can't be changed afterwards: what was deleted since it was made, like cycle records, is still in it until the backup itself is deleted.

Where the backups folder is on the server is the install's choice (BACKUP_DIR in .env; ./backups by default). Restoring one replaces the live data, so it's done on the server with the app stopped (python -m server.manage restore), never from this page. The watch receiver puts its data back when it's restarted after that. What a restore replaces is kept in the data folder for a while, then deleted: Restore, below, says when.
